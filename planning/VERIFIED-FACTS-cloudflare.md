# Cloudflare architecture — verified facts (2026-09-21)

Authoritative. Overrides any conflicting assumption.


## hyperdrive-supabase — WORKS_WITH_CAVEATS

Hyperdrive officially supports Supabase Postgres, and Cloudflare's own Supabase guide says to use the **Direct connection** string (`db.<ref>.supabase.co:5432`), not Supavisor — Hyperdrive is itself a transaction-mode pooler and double-pooling costs you named prepared statements. The one real gotcha: Supabase's direct endpoint is **IPv6-only** unless you buy the IPv4 add-on, so confirm Hyperdrive dials it or fall back to Supavisor session mode (`aws-<region>.pooler.supabase.com:5432`, IPv4, prepared statements OK) — never transaction mode 6543. Use `pg` (node-postgres) >= 8.16.3 with `nodejs_compat`; it is Cloudflare's recommended driver and has the best Hyperdrive cache compatibility. Query caching is **on by default at max_age=60s with no write invalidation**, so the x402 grant check and access decision MUST go through a second, separate `--caching-disabled` Hyperdrive config bound alongside the cached one — this is the documented pattern, not a workaround. The security posture is the load-bearing finding: **RLS does not protect you here**. I verified against the owner's own live Supabase Postgres 17 project that the `postgres` role has `rolbypassrls = true`, so a Worker connecting with the default connection string bypasses every RLS policy; there is no PostgREST, no JWT, no `request.jwt.claims`. Authorization must be enforced in Worker code, or you must provision a dedicated non-owner, NOBYPASSRLS login role plus `FORCE ROW LEVEL SECURITY` and per-transaction `SET LOCAL ROLE`. Hyperdrive is included in Workers Paid at no extra charge with unlimited queries, ~100 origin connections, and a 60-second statement cap. `LISTEN`/`NOTIFY`, advisory locks and SQL-level `PREPARE` are unsupported.

**Recommendation:** Adopt Hyperdrive, but change two things in the 18-section plan.

**Connection.** Give Hyperdrive the Supabase **Direct connection** string on port 5432 — that is Cloudflare's explicit guidance, and it preserves named prepared statements, which Hyperdrive's cache depends on. Validate the IPv6 question immediately and cheaply: `wrangler hyperdrive create` test-connects before it will create a config, so a successful create is your proof. If it fails, fall back to Supavisor **session** mode (`aws-<region>.pooler.supabase.com:5432`) — IPv4 on every tier and, unlike transaction mode, it supports prepared statements. Do not use port 6543 under any circumstance.

**Two bindings, not one.** Create `musebook-prod` (cached, max_age 60) and `musebook-prod-fresh` (`--caching-disabled`), bind both to the Worker, and instantiate a separate driver client per binding. The x402 grant check, the access decision, payment state, and every read-after-write go through `HYPERDRIVE_FRESH`. Public content bodies, teasers and catalog listings go through the cached binding. This is Cloudflare's own documented pattern for exactly this problem, and it is not optional: caching is on by default and Hyperdrive never invalidates on write, so a single binding would serve a paid agent a "no grant" answer for up to 75 seconds. Budget `--origin-connection-limit` across both pools (40 + 20 is a reasonable split) so the total stays inside your Supabase compute tier's connection budget.

**Rewrite the security section.** The plan should stop treating RLS as the authorization boundary at the edge. Through Hyperdrive there is no PostgREST, no JWT verification and no `request.jwt.claims`; `auth.uid()` returns null. Worse, I verified on the owner's own live Postgres 17 project that the `postgres` role has `rolbypassrls = true` — so the default connection string disables RLS wholesale. Do two things: (1) enforce authorization explicitly in Worker code — it is the honest model for an edge paywall, and it avoids the transaction-holding that Cloudflare warns degrades pool multiplexing; (2) keep RLS as defense-in-depth anyway by provisioning a dedicated `musebook_edge` login role with NOINHERIT/NOBYPASSRLS, granting it only the specific tables it needs (never `GRANT postgres TO ...`, despite what Cloudflare's own Supabase snippet shows), and setting `FORCE ROW LEVEL SECURITY` on every table — without FORCE, the `postgres` owner is exempt regardless. Keep a CI assertion on `pg_roles.rolbypassrls` and `pg_class.relforcerowsecurity` so a future migration cannot quietly undo it.

If you later want true per-user RLS from the edge, `authenticator` is the template — verified NOINHERIT, NOBYPASSRLS, member of anon/authenticated/service_role, so it can `SET ROLE`. Hyperdrive does support `SET` within a transaction or a single multi-statement query. But confine that pattern to the cache-disabled binding: Cloudflare documents nothing about whether the cache key incorporates the session role, and identical SQL under two roles on the cached binding is a plausible cross-tenant leak.

Finally, two smaller plan edits: drop any reliance on Postgres `LISTEN`/`NOTIFY` for job triggering — it is unsupported through Hyperdrive, and Cloudflare Queues already covers it — and turn on Smart Placement with `region: "aws:<supabase-region>"`, which Cloudflare says takes per-query latency from 20-30ms to 1-3ms once a request makes more than one query. Cost impact of the whole change is zero: Hyperdrive is included in Workers Paid with unlimited queries and no egress charge.

**Blockers:**
- IPv6-ONLY DIRECT ENDPOINT — the one thing to test before committing. Cloudflare says use Supabase's Direct connection (db.<ref>.supabase.co:5432), but Supabase documents that endpoint as IPv6-only on Free and Paid. No Cloudflare doc states Hyperdrive is IPv4-only, and Cloudflare's Fly.io guide actively recommends allocating an IPv6 address for a Hyperdrive origin — so this very likely works. I could not confirm by DNS from this sandbox (egress proxy blocked both DoH resolvers, and db.<ref>.supabase.co returned no A record locally, consistent with AAAA-only). RESOLUTION: run `npx wrangler hyperdrive create` with the direct string — Hyperdrive test-connects before it will create the config, so a successful create IS the proof. Error 2008/2010 means it failed. Safe fallbacks, in order of preference: (a) Supavisor SESSION mode, aws-<region>.pooler.supabase.com:5432, IPv4 on every tier and it DOES support prepared statements; (b) buy the IPv4 add-on, but note it is not dual-stack and swaps AAAA for A, which will break any existing IPv6 consumer; (c) Dedicated Pooler PgBouncer on db.<ref>.supabase.co:6543 — also IPv6, transaction mode only, no advantage over Hyperdrive.
- NEVER point Hyperdrive at Supavisor transaction mode (port 6543). It does not support prepared statements, and Hyperdrive's caching and performance depend on named prepared statements. You would be stacking two transaction poolers and paying for it twice.
- RLS IS NOT YOUR SECURITY BOUNDARY HERE — and I verified this on the owner's own live Postgres 17 Supabase project, not from memory: `postgres` has rolbypassrls = TRUE. Paste the default Supabase connection string into Hyperdrive and every RLS policy in the database becomes decorative. Cloudflare's own Supabase example makes this worse by suggesting `GRANT postgres TO hyperdrive_user` (its own comment admits 'In practice, you want to create a role with lesser privileges'). Do not copy that line. This is a hard prerequisite for the x402 paywall being trustworthy.
- TABLE OWNERSHIP IS A SECOND RLS BYPASS. Even a NOBYPASSRLS role is exempt from RLS on tables it owns. Supabase migrations create tables owned by `postgres`. You must set ALTER TABLE ... FORCE ROW LEVEL SECURITY and keep the edge role out of the owner position, or RLS silently does nothing.
- service_role CANNOT be used as a Hyperdrive login — verified rolcanlogin = false on the live project. Any plan that says 'connect as service_role' does not work.
- CACHE KEY + SET LOCAL ROLE IS AN UNVERIFIED INTERACTION. Cloudflare documents nothing about whether the query cache key includes the connection's current role or SET LOCAL state. If you do RLS-scoped SET LOCAL ROLE queries on the CACHED binding, identical SQL text under two different roles could in principle serve one user's cached rows to another. Treat this as a live cross-tenant leak risk: route every per-user or RLS-scoped query through HYPERDRIVE_FRESH, and keep the cached binding for role-independent public content only.
- LISTEN/NOTIFY DOES NOT WORK over Hyperdrive, nor do advisory locks or SQL-level PREPARE/DEALLOCATE/DISCARD. If any part of the async job pipeline was going to use Postgres LISTEN/NOTIFY as a trigger, it cannot — use Cloudflare Queues (already in the architecture) instead. Cloudflare's own fallback is a second direct client that bypasses Hyperdrive entirely.
- DEFAULT-ON CACHING IS A CORRECTNESS TRAP FOR x402. A single Hyperdrive config serves reads up to 60s stale (plus a 15s stale-while-revalidate window) with NO write invalidation. An agent that just paid could be told it has no grant, and a revoked grant could keep working for over a minute. The two-binding split is mandatory, and the grant check must be on the cache-disabled one.
- Long transactions starve the pool. Hyperdrive holds a connection for a whole transaction, so wrapping multiple operations in BEGIN/COMMIT to preserve SET state directly degrades multiplexing. Cloudflare says so explicitly. This puts real tension on the PostgREST-emulation approach to RLS — the in-code authorization path is both simpler and faster.
- Cloudflare's Supabase docs page is stale (reviewed 2024-01-09, still claims 'Supabase currently runs Postgres 15.x'). The engine support matrix covers PostgreSQL 9.0-17.x, so Postgres 17 is fine — but do not treat that page's specifics as current.
- pgvector queries: not separately tested here. Vector similarity SELECTs are non-mutating and therefore CACHEABLE, and a 60s stale ANN result may or may not matter to you. Large embedding result sets also brush the 50 MB cache ceiling and the 60s statement cap. Decide per query which binding it belongs on.


## r2-media-gating — WORKS_WITH_CAVEATS

R2 does everything Musebook needs for media and artifacts, but the gating architecture forces a bucket split, not a prefix split: a custom domain is bucket-wide and unconditionally public, so PAID media can never live in a bucket that has cdn.musebook.dev (or r2.dev) attached. Put FREE/teaser media in musebook-public behind cdn.musebook.dev (CDN cache hits cost $0 and never touch R2, so no Class B), and put paid media in musebook-paid with NO custom domain and NO public dev URL, reachable only through the Worker binding after an x402 grant check. Presigned URLs are the wrong tool for gating here — Cloudflare states explicitly that presigned URLs do not work with custom domains, so they leak <ACCOUNT_ID>.r2.cloudflarestorage.com, bypass your zone entirely (no cache, no bot gate, no pay-per-crawl, no analytics) and are freely shareable bearer tokens for up to 7 days; use them only for uploads. R2 range requests work natively via the binding (pass request.headers straight into R2GetOptions.range) and each HTTP range GET is one Class B op at $0.36/M — for 1,000 minutes of HLS-segmented video that is ~$0.0036 of R2 ops plus ~$0.003 of Worker requests, versus $1.00 on Cloudflare Stream, roughly 150x cheaper but with no encoding, no ABR ladder and no player. The one real blocker-shaped risk is policy, not technology: Cloudflare's own "Delivering Videos with Cloudflare" page says Free/Pro/Business CDN terms prohibit serving video and names only Stream and Enterprise Stream Delivery as sanctioned paths, with no carve-out for R2 custom domains — so long-form video on a Free-plan musebook.dev zone is exposed to a ToS redirect.

**Recommendation:** Split media across four buckets and route each by who may read it.

1. musebook-public + cdn.musebook.dev (R2 custom domain). FREE-tier media, teasers, posters, thumbnails, OG images, and the crawlable teaser assets for X402_ALWAYS content. No Worker in the path, so a CDN cache hit costs $0 in both Worker requests and R2 Class B. Add the Cache Everything rule (default caching skips .m3u8/.ts/.json) and enable Smart Tiered Cache. This is the cheapest byte-serving path Cloudflare offers and it is where the bulk of Musebook's traffic should land.

2. musebook-paid — no custom domain, no dev URL, binding only. Served through media.musebook.dev, which is a plain proxied AAAA 100:: record on a Worker route, not an R2 custom domain. Use the Workers-Caching gateway pattern: the default entrypoint always runs and performs the x402 grant check (KV lookup on agent_id + content_hash for HUMAN_FREE_AGENT_PAID, or a fresh PAYMENT-SIGNATURE verification for X402_ALWAYS), strips every payment/auth header, then calls ctx.exports.PaidMedia.fetch(). PaidMedia is cacheable and keyed on URL alone, so all paying agents share one cache entry while unpaid callers never reach it. This is the recommended serving path for paid media — build it, not presigned URLs.

3. musebook-artifacts — same treatment, behind artifacts.musebook.dev on the same Worker.

4. musebook-uploads — ingest only. Client-side multipart via presigned UploadPart URLs straight to <ACCOUNT_ID>.r2.cloudflarestorage.com, with the Worker only creating and completing the upload. Presigned URLs are the right tool here and the wrong tool for gating; keep the upload credential scoped to this bucket alone, and presign with a 900-second expiry rather than the 7-day maximum.

On range requests: pass request.headers directly into R2GetOptions.range and build Content-Range yourself from R2Range plus R2Object.size (the binding sets neither the 206 nor the header). Bypass Workers Caching whenever a Range header is present — caching partial responses is subtle and a direct binding read is $0.00000036. Each ranged GET is one Class B, so a full HLS view of a 10-minute video costs about $0.000036 in R2 ops.

On R2 vs Stream: R2 wins on raw cost by roughly 150x on delivery and 11x on storage, but Stream is not really competing on price — it is selling encoding, the ABR ladder, signed playback tokens, a player, and, decisively, ToS cover for video delivery. Recommendation: use R2 for images, audio, artifacts, and short clips (under ~60 seconds), and use Cloudflare Stream for long-form video, at least until Cloudflare confirms in writing that R2-origin video on a Free-plan zone is fine. Stream also solves the paid-video gating problem independently via signed URLs, and its videos are not attached to a zone, so they sidestep the CDN video restriction entirely. Budget Stream at $5 per 1,000 minutes stored plus $1 per 1,000 minutes delivered and model it against expected watch minutes before committing; if long-form video is central to Musebook, that line item, not R2, is the one that will dominate the bill.

On lifecycle and IA: apply --abort-multipart-days 2 on musebook-uploads immediately (abandoned browser uploads are silent Class A spend for 7 days by default), expire staging/ and scratch/ prefixes, and restrict --ia-transition-days to a masters/ prefix holding cold originals. Do not put delivery renditions in Infrequent Access: the 30-day minimum duration, $0.01/GB retrieval and 2.5x Class B rate make IA a net loss for anything read more than about once every two months.

One thing to correct in the 18-section plan: the plan's likely assumption that artifacts.musebook.dev and cdn.musebook.dev are both R2 custom domains is wrong for anything gated. Only cdn is an R2 custom domain. media and artifacts are Worker routes on ordinary proxied DNS records, and the buckets behind them must never have a custom domain or dev URL attached — add the two `wrangler r2 bucket domain list` / `dev-url get` checks above to CI so a future change cannot silently unseal the paid bucket.

**Blockers:**
- POLICY, not technical: Cloudflare's 'Delivering Videos with Cloudflare' page (updated 2026-08-25) states that Free/Pro/Business plan zones serving video or a disproportionate amount of large files without an appropriate paid video service may have their content redirected, and names only Cloudflare Stream and Enterprise-only Stream Delivery as sanctioned paths. There is no documented R2 carve-out. Long-form video served from R2 through a Free-plan musebook.dev zone (whether via cdn.musebook.dev or media.musebook.dev) sits in this grey zone. This does not block images, audio, thumbnails, JSON artifacts or short clips.
- Presigned URLs cannot be used for the x402 paywall. Cloudflare states outright that presigned URLs do not work with custom domains — a presigned link exposes <ACCOUNT_ID>.r2.cloudflarestorage.com, routes around the musebook.dev zone entirely (no Cloudflare cache, no bot gate, no pay-per-crawl, no Web Bot Auth verification, no URL analytics), and is a shareable bearer token valid for up to 7 days. The intended per-agent, per-content_hash x402 grant model cannot be enforced this way.
- A custom domain publishes the WHOLE bucket. There is no per-prefix authorization on an R2 custom domain. If paid media shares a bucket with cdn.musebook.dev, every paid object is fetchable by guessing its key, and the x402 gate is decorative. The bucket split is mandatory, not a preference.
- The documented non-Worker way to authenticate a custom domain is WAF Token Authentication (is_timed_hmac_valid_v0), which requires Pro plan or above — and it still cannot evaluate an x402 payment receipt. It is not an alternative to the Worker for Musebook.
- The exact Workers inbound request body size limit (which caps how large a part a Worker can proxy into R2) could not be retrieved in this environment; developers.cloudflare.com and vercel.com are blocked by the HTTP egress proxy and the docs MCP did not surface the number. Safe fallback: never proxy uploads through the Worker — presign each UploadPart and have the client PUT directly to the S3 endpoint, which the R2 limits footnote confirms is not subject to the Worker limit.


## queues-vs-pgmq — WORKS_WITH_CAVEATS

Cloudflare Queues is the right async spine for the Worker-side of the split, and its real limits are comfortably above anything Musebook will produce (5,000 msg/s per queue, 25 GB backlog, 10,000 queues per account, 250 concurrent consumers, 15 min wall clock per consumer invocation). It is also nearly free at your scale: ~$0.40 per million 64 KB operations with 1M ops/month included on Workers Paid, so 2M jobs/month costs about $2. The one thing it genuinely cannot do is join a Postgres transaction, and that loss is real but narrower than it looks — Queues is at-least-once with no exactly-once mode, so every consumer needs an idempotency gate regardless, and once you have that gate the transactional-enqueue problem collapses into "a job row may exist with no message," which a one-minute Cron sweep fixes. The correct pattern is a transactional outbox written in the SAME single statement as the domain row (a data-modifying CTE or one plpgsql function call — NOT an explicit BEGIN/COMMIT, because Hyperdrive explicitly warns that pinning a pooled connection across round trips degrades its pool), plus best-effort enqueue-after-commit in ctx.waitUntil, plus a Cron Worker sweeper. Move classification, media generation, distribution/Postiz fan-out and embeddings to Queues; keep the outbox and the rollups in Postgres (pg_cron), and keep anything in the x402 settlement path out of Queues entirely.

**Recommendation:** Move to Cloudflare Queues: classification, media generation, distribution/Postiz fan-out, embedding generation, and any R2-object-created derivative work. Keep in Postgres: the outbox table itself, and the rollups.

The honest read on the transactional-enqueue question. The loss is real but it is a recovery-latency problem, not a correctness problem, and only if you keep the outbox row. Here is why it matters less than it first appears: Queues is at-least-once with no exactly-once mode, so every consumer needs an idempotency gate no matter what you do. pgmq does not save you from that either — its "exactly once within a visibility timeout" is a visibility-window property, and a consumer that crashes mid-work still gets a redelivery. So you were always going to write the claim-or-ack gate. Once it exists, the only thing transactional enqueue was buying you is "a job row never exists without its message," and a `* * * * *` Cron sweep over a partial index reduces that to a bounded ~60-second delay on a path that essentially never fires. That is a good trade for getting DLQs, delaySeconds backoff, 250-way autoscaling, 15-minute consumer runtime, and R2 event sources — none of which pgmq has without you building them.

The pattern, precisely: write the domain row and its outbox row in ONE statement (data-modifying CTE, or a plpgsql function invoked with a single `select`). Do not use an explicit `BEGIN`/`COMMIT` from the Worker — Hyperdrive's own docs say a transaction held across round trips pins the pooled connection and degrades the pool, and that pool is only ~100 connections wide. Then enqueue AFTER the commit, inside `ctx.waitUntil`, wrapped in try/catch that swallows failures. Then sweep. Never enqueue before the commit: that produces messages for rows that may never exist, the consumer cannot distinguish "not committed yet" from "rolled back," and it burns retries against phantom work.

Per-job-type calls:
- Classification, embeddings: pure Queues. Low stakes, batchable. Embeddings especially — `max_batch_size: 100` is the hard ceiling and maps 1:1 onto a batched embeddings API call. Reconciliation is trivial anyway (`posts LEFT JOIN classifications WHERE ... IS NULL`), so the sweeper is belt-and-braces.
- Media generation: Queues, with `max_batch_size: 1` and `max_concurrency: 10`. Duplicates here cost real GPU money, so the claim-or-ack gate earns its keep, and you should additionally make output keys content-addressed (`renders/{content_hash}/{variant}`) so a duplicate run overwrites identical bytes instead of creating a second artifact and a second charge.
- Distribution / Postiz fan-out: Queues, and this is the one where at-least-once bites hardest — a duplicate here publishes to a real social account twice, which is user-visible and unrecoverable. Insert a `unique (post_id, channel)` row BEFORE the outbound call, not after, and pass Postiz its own idempotency key if the API accepts one. `retry_delay: 60` plus a DLQ handles their rate limits.
- Rollups: do NOT move these. They are pure SQL on a schedule that touch no external service. `pg_cron` calling `refresh materialized view concurrently` is simpler, cheaper, and has one fewer network hop than a Cron Worker reaching back through Hyperdrive. Moving them to Queues adds cost and failure modes for nothing.
- x402 settlement: keep entirely out of Queues. Whether an agent has paid for a `content_hash` must be a Postgres row written in the same transaction as the settlement record, read synchronously on the paywall path. If you need async retry around settlement, that is the one place to keep pgmq.

So: pgmq does not disappear from the plan, it shrinks to two things — the outbox (which is really just a table, you need not even install pgmq for it) and the x402 settlement retry path. Everything else moves.

Two things to get right at build time that are easy to miss: use two Hyperdrive configurations and point the sweeper at the cache-disabled one, because Hyperdrive caches reads and does not invalidate on write, so a cached sweeper would re-enqueue a stale `pending` set forever. And ship a DLQ consumer with the very first queue — an unconsumed DLQ silently deletes its messages after four days, which is the worst possible way to discover you had a bug.

Finally, worth naming but not adopting as the spine: Cloudflare Workflows is a better fit than Queues for the multi-step media pipeline specifically (durable steps, `step.sleep`, automatic retry per step), if the generation flow grows past submit-and-collect. It bills separately on steps ($0.80 per additional 100,000 beyond 500,000/month) so it is not free, and it does not change the transactional story at all — you would still enqueue the Workflow from the outbox. Revisit it only if the media pipeline exceeds three or four dependent stages.

**Blockers:**
- None that make the split architecture impossible. Everything below is a design constraint that the recommended pattern already handles.
- Hard constraint: Cloudflare Queues has no transactional producer and cannot join a Postgres transaction. Any plan that assumes 'insert the post and enqueue the job atomically' with Queues alone is wrong and must be rewritten as outbox + sweeper.
- Hard constraint: Queues is at-least-once with no exactly-once mode, and a queue can have exactly one active consumer. Every consumer MUST be idempotent. This is not optional and it is not a property you can configure away.
- Hard constraint: Hyperdrive's docs explicitly advise against multi-round-trip explicit transactions from a Worker. This rules out the naive `BEGIN; insert post; insert outbox; COMMIT;` outbox implementation. The outbox write must be a single statement (CTE or plpgsql function call).
- Hard constraint: a consumer invocation cannot exceed 15 minutes of wall clock. Any media generation that can exceed 15 minutes must be split: the consumer submits to the GPU vendor and records a handle, and a second job (or the vendor's webhook into the Worker) collects the result. Do not design a consumer that blocks on a long poll.
- Hard constraint: 128 KB per message. Media payloads, full transcripts and embedding inputs must be passed by R2 key or Postgres row id, never inline.
- Operational constraint: the Vercel-hosted Next.js frontend has NO Queues binding. It must write through the Worker origin (correct), or fall back to the Queues HTTP publish API with a 'Queues Edit' token (possible, but it bypasses the outbox and should be avoided).
- Operational gap to not forget: an unconsumed DLQ deletes its messages after 4 days. Ship a DLQ consumer with the first queue, not later.


## web-bot-auth — WORKS_WITH_CAVEATS

Web Bot Auth is real, shipping, and verifiable inside a Worker today — but Cloudflare will NOT do the verification for you unless Musebook is on Enterprise Bot Management, so the Worker must verify the Ed25519 signature itself. That is fully supported: workerd implements Secure Curves Ed25519 in `crypto.subtle` (importKey/verify) with NO compatibility flag and no `nodejs_compat`, and Cloudflare publishes a first-party, zero-Node-dependency npm package — `web-bot-auth@0.2.0` (Apache-2.0, deps: `http-message-sig@0.3.0`, `jsonwebkey-thumbprint@0.1.0`, `structured-headers@2.0.3`) — whose own reference implementation is a Cloudflare Worker. The protocol is RFC 9421 HTTP Message Signatures plus a `Signature-Agent` header and a JWKS at `/.well-known/http-message-signatures-directory`, keyid = RFC 7638/8037 JWK thumbprint, `tag="web-bot-auth"`. The big caveat for the HUMAN_FREE_AGENT_PAID mode is coverage: in Sept 2026 only a handful of agents sign (OpenAI's ChatGPT agent/Cloud browser, Google-Agent — not Googlebot, AWS Bedrock AgentCore Browser, Cloudflare Browser Run), the IETF WG has adopted zero documents, and an agent that simply omits the headers is indistinguishable from a human at the edge. Second caveat: signatures normally cover only `@authority`, not the path — so a captured signature is replayable across your whole domain for its validity window. Treat Web Bot Auth as positive agent identification, never as authorization, and never as proof that an unsigned request is human.

**Recommendation:** Build the Worker to verify signatures itself, with `web-bot-auth@0.2.0`. Do not budget for Enterprise Bot Management, and do not design around `request.cf.botManagement` — plan for it to be null.

Concretely, the plan should say:

1. **Dependency**: pin `web-bot-auth@0.2.0` (+ its three transitive deps) exactly. It is Cloudflare's own, Apache-2.0, pure-WebCrypto, zero Node imports, and its reference implementation IS a Worker. Do not hand-roll RFC 9421 unless you have a hard no-dependency rule — the `;key=` dictionary-member and `;req` component serializations are where hand-rolled implementations get quietly wrong.

2. **No compatibility flag**. `compatibility_date` can be anything current; `nodejs_compat` is not needed for this path (add it only if `x402/core@2.26.0` demands it).

3. **Override the library's loose defaults**: `algorithms: ["ed25519"]`, `maxAge: 300`, `clockSkew: 30`. The shipped default of `maxAge: 86400` would let a captured signature work for a day.

4. **Allowlist Signature-Agent origins.** Keep the list in KV so you can add a signer without a deploy, seeded with chatgpt.com/openai.com, agent.bot.goog, and the Cloudflare Browser Run worker directory. Reject non-https, cap body at 64 KB and keys at 100, and use a 2 s fetch timeout. This is the single most important security decision in the whole feature.

5. **Cache directories in KV**, keyed by agent origin: honour the directory's `Cache-Control: max-age` clamped to [5 min, 24 h] (default 1 h), keep the record for 7 days as a stale fallback, and read with `cacheTtl: 300` so the hot path costs nothing. Negative-cache unknown keyids for ~60 s so a flood of forged keyids cannot make you hammer a third party.

6. **Fail direction — this is the question you asked, and the answer is asymmetric.** Presence of a `Signature` header is itself a declaration of botness, so the fail-open/fail-closed split runs on that boundary, not on fetch success:
   - No `Signature` header → human path, serve free. (Fail open — you have no better signal.)
   - Signature present and verifies → agent, charge x402 once per (keyid, content_hash).
   - Signature present but invalid/expired/unknown key → **401, never free**. A broken signature is strictly more suspicious than no signature.
   - Signature present but the directory is unreachable and no stale copy exists → **503 + `Retry-After: 30`, never free**. Serving free content here is exactly the failure a scraper would engineer by DoS-ing the agent's key directory. With a 7-day stale window this path should essentially never fire.

7. **Do not treat a verified signature as authorization.** It covers `@authority` only. Verify identity at the edge, then do all x402 accounting against `(keyid, content_hash)` in Supabase via Hyperdrive. If you need replay protection beyond the 5-minute window, add a Durable Object nonce cache keyed on the 64-byte nonce — but given the charge is idempotent per content_hash, that is probably over-engineering for v1.

8. **The Cloudflare verified-bot list is a weak, secondary signal and should be scoped as such.** There is no free per-request API. The Radar bots API (`GET /radar/bots`, token-authenticated) gives you the BotBase directory as metadata — operator, category, user-agent patterns — which you can sync into KV nightly and use for user-agent-pattern matching on UNSIGNED requests. It guarantees only that Cloudflare once approved a bot with that user-agent string; a user-agent is trivially forged, so it must never unlock paid content or downgrade an agent to human. Use it for analytics, robots.txt policy, and rate-limit tiering. Do not ship the CC BY-NC `cloudflare-bot-directory` npm package — Musebook is commercial.

9. **Set expectations in the plan doc**: HUMAN_FREE_AGENT_PAID will monetize a small, named set of signing agents today and grow as adoption does. If the business case needs to capture unsigned AI traffic too, X402_ALWAYS (402 on every visit with a crawlable teaser) is the only mode that actually does that, and it should be the default for high-value content. Cloudflare pay-per-crawl (PPC) is a feature of AI Crawl Control that returns HTTP 402 with a `crawler-price` header to verified AI crawlers and charges them per successful 200, with Cloudflare acting as Merchant of Record and paying publishers out via Stripe. No grant → x402 v2 PAYMENT-REQUIRED; on a valid PAYMENT-SIGNATURE settled in Base mainnet USDC, write the grant + ledger row, return 200 with PAYMENT-RESPONSE. Pay-per-crawl literally cannot do this — it charges every 200 and has no content_hash dimension.

Why not pay-per-crawl, stated in one line for the plan: it is closed beta, Cloudflare is Merchant of Record so Cloudflare sets the rail and receives the money in USD via Stripe with an undisclosed cut, and its pricing model (per-zone USD, per-200) cannot express Musebook's per-agent-per-content_hash USDC grant. ## x402-on-workers — WORKS_WITH_CAVEATS

Running the x402 v2 paywall inside a Worker works, and better than the plan assumes: the resource-server half of the SDK is workerd-native. I traced the full import graph of `@x402/evm@2.26.0/exact/server` — it pulls in exactly two local chunks plus `@x402/core/utils`, and **zero external packages: no viem, no Node built-ins**. `@x402/core@2.26.0` has a single dependency (`zod ^3.24.2`) and reaches the facilitator through global `fetch`. All EIP-712 work (`hashTypedData`, `recoverAddress`, `recoverTypedDataAddress`, `parseErc6492Signature`) and all `createPublicClient` usage live in the *facilitator* subpaths, which you do not import. So question (4) and (5) dissolve: you never recover a signature at the edge and no settlement key ever lives in a Worker. The caveats are real though. Cloudflare ships **no** x402 Worker template — `github.com/cloudflare/x402-proxy` is a 404; the only Deploy-button proxy is `cloudflare/mpp-proxy`, which is MPP, not x402. Cloudflare's own x402 code (`agents/x402` → `withX402`, `paidTool`, `withX402Client`) is v2 but is **MCP-only** (it lives at `dist/mcp/client/x402.js`), so it covers Musebook's remote MCP server and does nothing for the HTTP page gate. The default facilitator `https://x402.org/facilitator` does not settle Base mainnet, so you must onboard to Coinbase CDP. And the plan's KV-in-front-of-Postgres grant cache is unsafe as written — KV's up-to-60s cross-region window plus its caching of negative lookups can double-charge a paying agent.

**Recommendation:** Run the paywall in the Worker, but restructure three things.

1. TREAT THE RESOURCE SERVER AND THE FACILITATOR AS SEPARATE HALVES, and only ship the first to the edge. Depend on `@x402/core@2.26.0` and `@x402/evm@2.26.0` but import `@x402/evm/exact/server` and `@x402/core/server` / `@x402/core/http` by subpath. That path has zero external dependencies, no Node built-ins, no viem, and uses global `fetch` to reach the facilitator. The plan's `packages/x402` is therefore viable on workerd essentially for free — but add a bundle-level guard (an esbuild `external`/alias that throws on `viem`, `node:fs`, `node:path`) so nobody later writes `import { ... } from "@x402/evm"` against the root barrel and silently pulls in viem plus the fs-backed batch-settlement code.

2. NO KEY AT THE EDGE, AND NO EIP-712 AT THE EDGE. Questions (4) and (5) are moot: signature recovery and on-chain settlement live entirely in `@x402/evm/exact/facilitator`, which you do not import. Delegate both to the Coinbase CDP facilitator at `https://api.cdp.coinbase.com/platform/v2/x402`. Authenticate with `FacilitatorConfig.createAuthHeaders` — it is keyed by request path, so mint the CDP JWT yourself with WebCrypto and keep `@coinbase/cdp-sdk` and viem out of the Worker. Store the CDP API key id/secret in Secrets Store (`secrets_store_secrets`), not `vars`. Drop the default `timeoutMs` from 90,000 to ~20,000. Because `settle()` timeout is documented as an indeterminate outcome, push settlement confirmation into a Queue consumer that reconciles against the tx hash rather than trusting the edge response — this is where the plan's Queues binding earns its place.

3. REBUILD THE GRANT LOOKUP AROUND WHAT EACH MODE ACTUALLY NEEDS. X402_ALWAYS has no grant lookup at all (402 every visit), so KV is irrelevant there; just make sure the teaser is served with a 200 for crawlers, since Cloudflare AI Search hard-fails on 402 with `blocked_by_payment`. FREE bypasses the gate entirely. Only HUMAN_FREE_AGENT_PAID needs the lookup, and its grants are one-time and permanent per (agent, content_hash) — append-only, never revoked. That property is what makes KV safe, but only in one specific shape: POSITIVE-ONLY cache, keyed `g:{content_hash}:{agent_address}`, with a long `cacheTtl` (86400) since a present key can never become wrong. A MISS IS NEVER AUTHORITATIVE — on miss, always fall through to Postgres over Hyperdrive, and backfill KV with `ctx.waitUntil` after the authoritative read. Never write a tombstone or cache a negative; KV caches negative lookups at the edge and that is precisely the 60-second window that double-charges a paying agent. If you ever add grant revocation or expiry, this whole scheme breaks and you must move to a Durable Object.

The actual double-charge guard is not a cache at all — it is a unique index on `(content_hash, lower(agent_address))` in Postgres, written with `ON CONFLICT DO NOTHING` in the same transaction as the settlement tx hash, plus x402's own nonce replay protection at the facilitator. Treat KV strictly as a latency optimization that can be deleted at any time without changing correctness. For the settle-then-grant critical section itself, put a Durable Object keyed by `content_hash:agent_address` in front: it is single-threaded and strongly consistent, so two concurrent retries from the same agent in different regions serialize instead of both reaching `settle()`.

Two deployment details that will otherwise bite: build the server inside the fetch handler with a memoized promise (`initialize()` does network I/O and Workers forbid that in global scope; clear the memo on failure so a cold-start facilitator blip is not cached forever), and create the Hyperdrive/postgres client per request rather than caching it globally. Finally, before freezing this, have someone open developers.cloudflare.com/agents/tools/payments/x402/charge-for-http-content/ in a browser — that page is egress-blocked and absent from the docs search index here, and it is the one source that might describe a Cloudflare-blessed x402 Worker pattern I could not see.

**Blockers:**
- The plan's grant-cache design is unsafe as written. 'Check an access_grants row on every gated request' with KV as a read-through cache will double-charge: agent pays in IAD, the grant row is written, the agent's retry lands in FRA, KV there has either no key or a cached negative lookup for up to 60 s, so the Worker issues a second 402 and the agent pays again. KV negative-lookup caching makes this worse than a plain cold miss. Fix is in the recommendation — positive-only cache, Postgres authoritative on miss, unique index as the real guard.
- Cloudflare ships no x402 HTTP Worker template. github.com/cloudflare/x402-proxy is a 404; the only Deploy-button proxy is cloudflare/mpp-proxy, which speaks MPP (WWW-Authenticate: Payment), a different protocol. If the plan budgeted 'deploy Cloudflare's x402 proxy template', that line item does not exist — the gate Worker is bespoke code against @x402/core + @x402/evm/exact/server.
- Cloudflare's own x402 helpers (withX402, paidTool, withX402Client) are MCP-only — they live at agents/dist/mcp/client/x402.js. They cover Musebook's remote MCP server and contribute nothing to the HTTP page gate. Two separate integrations, not one.
- The default facilitator https://x402.org/facilitator does not settle Base mainnet. Shipping with FacilitatorConfig.url unset works in dev against Base Sepolia and then fails at settle() in production. Base mainnet requires onboarding to Coinbase CDP (API key + JWT auth) or self-facilitating — which is a real dependency with a signup, credentials and per-transaction cost, not a config line.
- x402HTTPResourceServer.initialize() performs network I/O (facilitator /supported). Workers forbid async I/O in global scope ('Disallowed operation called within global scope'). Any plan code that constructs and initializes the server at module top level will not deploy.
- The x402 doc page Cloudflare links at /agents/tools/payments/x402/charge-for-http-content/ could not be read — developers.cloudflare.com is egress-blocked and the page body is absent from the docs MCP search index. Anything that page says about a Cloudflare-blessed x402 Worker pattern is UNVERIFIED here and should be re-checked from a browser before the architecture is frozen.


## vercel-behind-cloudflare — WORKS_WITH_CAVEATS

The topology works and is the only way to get a Worker into the request path for musebook.dev, because Cloudflare partial/CNAME setup is Business+ ($200/mo) and full NS delegation is free — so moving NS to Cloudflare while Vercel stays registrar is correct. Four things must be right or it breaks: (1) the apex record must be whatever the Vercel project's domain card shows (Vercel now issues per-project dynamic targets like xyz.vercel-dns-016.com and anycast IPs from a pool such as 216.198.79.1; the legacy cname.vercel-dns.com / 76.76.21.21 still work), proxied, with Cloudflare flattening the apex CNAME automatically; (2) SSL/TLS mode must be Full (strict) — Vercel's CDN unconditionally 308-redirects HTTP to HTTPS, so Flexible produces a guaranteed ERR_TOO_MANY_REDIRECTS loop; (3) Cloudflare's default cache behavior already refuses to cache HTML/JSON (DYNAMIC, extension-based), which is a safety net for the paywall but means /_next/image is uncached and every image hits Vercel unless you add a Cache Rule; (4) the Worker must call fetch(request) with global_fetch_strictly_public NOT enabled — the default routes a same-zone subrequest straight to the zone origin (Vercel), ignoring Workers and bypassing Cloudflare security settings, so there is no 1019 loop. The real damage is not caching: Vercel overwrites x-forwarded-for and only honours a real client IP for Enterprise trusted-proxy customers, so every Vercel-side IP feature (WAF IP rules, IP rate limiting, x-vercel-ip-country geo, analytics geography) sees Cloudflare PoP IPs and is effectively dead. And the Vercel origin stays publicly reachable at *.vercel.app, so the x402 paywall is bypassable unless the Worker injects a shared secret that Next.js middleware enforces. I would still keep the frontend on Vercel — but only with the origin-lockdown header and with all IP-based defense moved to Cloudflare.

**Recommendation:** Build it — but build it with the four non-negotiables, and be honest that the seam costs you Vercel's security layer.

Do this:
1. Delegate musebook.dev to Cloudflare nameservers (Vercel stays registrar, exactly as with wzrd.tech). Partial setup is Business+ at $200/mo, so there is no cheaper path to getting a Worker in front.
2. Proxy the apex with a CNAME to the value on the Vercel project's domain card — not a memorized value; Vercel now issues per-project targets. Cloudflare flattens the apex CNAME automatically.
3. Set SSL/TLS to Full (strict) before you ever point the record. Vercel 308-redirects HTTP to HTTPS unconditionally, so Flexible is a guaranteed redirect loop, and Full (non-strict) validates nothing while Vercel is already serving a publicly-trusted cert.
4. Do not enable global_fetch_strictly_public. The default same-zone routing sends fetch(request) straight to Vercel with no loop. Note the corollary: that subrequest bypasses Cloudflare's own security settings, so all gating must complete in Worker code before the fetch.

On caching, the good news is that Cloudflare's defaults are already the correct posture for a paywall: HTML and JSON are DYNAMIC (uncached), Set-Cookie responses are uncached, 402 is not in the default-cached status set. You get double-caching bugs only if you go out of your way to create them. So: use the vendor-prefixed headers — Cloudflare-CDN-Cache-Control for the Cloudflare layer, Vercel-CDN-Cache-Control for the Vercel layer, plain Cache-Control for the browser — and never emit a bare CDN-Cache-Control, which both CDNs read. For any 402-able route use Vary: * (the one Vary form Cloudflare honours unconditionally) plus no-store in all three headers plus a Bypass-cache Cache Rule. Four independent belts, because the failure mode is publishing paid content to a shared cache. Never apply an override_origin Edge TTL to a gated path prefix — it is documented to override no-store. Add cache_deception_armor everywhere HTML is cacheable. Add a Cache Rule for /_next/image or you will pay Vercel for every image request forever, since that path has no file extension and Cloudflare will not cache it. Turn Polish and Mirage off.

ISR and revalidateTag keep working; Cloudflare just does not know about them. Since purge-by-tag went to all plans in April 2025, emit Cache-Tag from the Worker and fire a Cloudflare tag purge in the same handler that calls revalidateTag. That closes the staleness seam properly rather than papering over it with a 60-second TTL.

The two things I would push back on if this were my system: the Vercel origin is still open at *.vercel.app, so ship the shared-secret header and the middleware 404 in the same PR as the paywall, not later — without it the gate is decorative. And accept that Vercel's WAF, IP rate limiting, geo headers and analytics geography are gone, because Vercel only forwards the real client IP to Enterprise trusted-proxy customers. Move all of that to Cloudflare and rewrite any Vercel-side rate limiting to key on CF-Connecting-IP.

Would I recommend hosting the frontend on Cloudflare too? Honestly: architecturally yes, pragmatically no. One platform would collapse two request-billing surfaces into one, keep the real client IP end to end, give the Worker native access to R2 and Queues without a network hop, and delete the certificate, redirect-loop, Invalid-Configuration and origin-bypass classes of problem entirely. But Next.js 16 on Workers via OpenNext is a meaningfully different runtime with its own ISR and image-optimization story, and the plan's other 17 sections assume Vercel. The seam is a bad idea in the abstract and an acceptable one here, because it is small, well-understood, and every one of its failure modes has a concrete mitigation above. Keep the frontend on Vercel, implement the mitigations as launch blockers rather than follow-ups, and add a synthetic check that asserts a known gated URL still returns 402 — that one check is what catches somebody grey-clouding the DNS record and silently removing your entire paywall.

**Blockers:**
- None that make the topology impossible. The following are hard constraints the plan must design around rather than blockers.
- HARD CONSTRAINT (security): the Vercel origin stays publicly reachable at <project>.vercel.app. The Worker-based x402 paywall is bypassable by any agent that finds that hostname. This is not fixable with DNS or Cloudflare settings — it requires the x-musebook-edge shared-secret header plus Next.js middleware that 404s anything lacking it (see exact_config section 4). Ship the paywall without this and the gate is decorative.
- HARD CONSTRAINT (Enterprise-gated): Vercel will not give you the real client IP behind a proxy on any plan below Enterprise. Every Vercel-side IP feature is dead in this topology: WAF IP rules, WAF IP-keyed rate limiting, x-vercel-ip-country/region/city/lat/long/timezone, geolocation(), ipAddress(), Vercel's own DDoS mitigation. - COSMETIC BUT PERSISTENT: Vercel's domain card will likely read 'Invalid Configuration' forever because it resolves musebook.dev to Cloudflare anycast IPs. Serving and certificates still work. Document this so nobody 'fixes' it by grey-clouding the record and silently removing the Worker from the request path — which would disable the entire paywall without any alarm firing. Add a synthetic check that asserts a known 402 path still returns 402.

## workers-runtime — WORKS_WITH_CAVEATS

The Musebook portable core runs on workerd with no blockers. As of compatibility_date 2026-08-04 or later, `nodejs_compat` and `nodejs_compat_v2` are ON BY DEFAULT — the plan should pin `compatibility_date = "2026-09-21"` and needs no compat flags at all; `node:crypto` is fully supported (only argon2, ed448/x448 and DSA/DH keygen missing), so packages/content can use either `node:crypto` sha256 or WebCrypto. Ed25519 IS in workerd's WebCrypto (plus the legacy `NODE-ED25519` alias); secp256k1 is NOT and never will be — EVM/x402 signature verify must go through `@noble/curves`, which viem already bundles, so this is a non-issue in practice. CPU is emphatically not the constraint on the 200-candidate ranking pass: the scoring math is roughly 307k multiply-adds and ~1 ms against a default budget of 30,000 ms (raisable to 300,000 ms), and 200 × 1536-dim float32 embeddings are 1.2 MB against a 128 MB isolate. The real constraints are that the 128 MB is PER ISOLATE shared across all in-flight requests (so per-request embedding loads multiply under concurrency), and that fan-out is capped at 6 SIMULTANEOUS OPEN CONNECTIONS per request — not by the 10,000 subrequest limit everyone quotes. I therefore recommend firmly that the mixer run in a Queue consumer / Cron Worker that writes a slate, with the request path doing a single read. On dependencies: every package checks out, but two things in the plan are wrong — `@cloudflare/vitest-pool-workers` is superseded by `@cloudflare/vitest-plugin` with a `cloudflareTest()` Vite plugin, and it peer-requires vitest ^4.1.0 while vitest latest is 5.0.1, so section 17 must pin vitest 4.1.11 or it will not install.

**Recommendation:** Nothing in the portable core blocks the split architecture — ship it, but change six things in the plan.

(1) PIN compatibility_date = "2026-09-21" AND DELETE the nodejs_compat flag from the plan's wrangler configs. Since 2026-08-04 both nodejs_compat and nodejs_compat_v2 are enabled BY the compatibility date; listing them is dead config that implies a control you no longer have. If you want the conservative floor instead, 2026-08-04 is the first date with this behavior.

(2) ON THE RANKING PASS — run it in the Queue consumer, not the request path. FIRM. But reject the stated reason: CPU is not the constraint and is not close. 200 candidates is ~1 ms of scoring against a 30,000 ms default. The three things that actually argue for offline are (a) the 6-simultaneous-connection cap, which serializes a fan-out over N candidate sources into ceil(N/6) latency waves regardless of the 10,000 subrequest headroom; (b) the 128 MB budget being PER ISOLATE shared across every in-flight request, so 1.2 MB of per-request embeddings is harmless at 1 concurrent request and a recycling isolate at 100; and (c) pgvector kNN over Hyperdrive adding a database round trip to every page view — including the x402 402-response path, which must stay fast because bots retry it. So: musebook-mixer consumes musebook-mix and writes a Slate to KV; musebook-edge does one KV get and enqueues a refresh via ctx.waitUntil on a stale hit. Keep packages/muse-mixer pure, as designed, so the identical code can run inline behind a flag for cold/uncached personalization with limits.cpu_ms capped low — the purity is what makes this a runtime choice rather than a rewrite.

(3) CRON SCHEDULING GOTCHA: if you add a cron for slate rebuilds, use an interval of >= 1 hour ("0 * * * *") to get a 15-minute CPU budget. A */15 or */5 cron silently caps at 30 seconds of CPU. Prefer the Queue for the real work and let cron only enqueue.

(4) CRYPTO IS FINE, with one correction to make in the plan: Ed25519 is native in WebCrypto (use "Ed25519", not the legacy "NODE-ED25519"), and node:crypto is fully supported so packages/content can use either. secp256k1 is NOT in WebCrypto and will not be — route EVM/EIP-712 verification through viem/@noble/curves, which you already have transitively. For content_hash over R2 media, use the Cloudflare-specific crypto.DigestStream rather than buffering the object, or a large asset will push the isolate toward 128 MB.

(5) FIX THE TEST STACK BEFORE WRITING SECTION 17. @cloudflare/vitest-pool-workers and defineWorkersConfig/defineWorkersProject are gone. Use @cloudflare/vitest-plugin 1.2.0 with the cloudflareTest() Vite plugin, and PIN vitest to 4.1.11 — the plugin peer-requires ^4.1.0 and vitest latest is 5.0.1, so an unpinned install fails outright. isolatedStorage/singleWorker no longer exist. Add wrangler's createTestHarness() for the edge-Worker-in-front-of-origin integration tests, which vitest-plugin does not cover well. Run the pure packages (kernel, muse-mixer, content) under BOTH plain vitest and cloudflareTest() — the second run is your portability gate, and it is the only thing that will catch a node: import creeping into a package that is supposed to have zero platform imports.

(6) DEPENDENCY CORRECTIONS. Drop mcp-handler 2.2.0 from the Worker — it is a Next.js adapter; use @modelcontextprotocol/server 2.0.0, which ships an explicit "workerd" export condition and a ./validators/cf-worker entry, and use that validator rather than ./validators/ajv. Never bundle @x402/paywall into the Worker (React 19 + wagmi + WalletConnect + Solana + Algorand); it is a Next.js-side package. Use @x402/hono for the Worker middleware. Avoid the two @x402/evm batch-settlement file-storage subpaths and avoid viem/node — both are the only fs/net-touching paths in those packages, and both are subpath-isolated, so this costs you nothing. Switch Hyperdrive to pg ^8.23.0 rather than postgres.js: Cloudflare explicitly recommends node-postgres as having the best compatibility with Hyperdrive's caching, though postgres@3.4.9 does ship a real workerd build if you prefer it.

TWO THINGS TO WATCH THAT ARE NOT YET PROBLEMS. First, the 1-second STARTUP budget is the limit Musebook is most likely to hit, and the docs name your exact failure mode: "generating or consuming a large schema at the top level." You will have zod schemas from @x402/core, MCP tool schemas, and kernel schemas all at module scope in one Worker. Build the schema-heavy MCP server as a SEPARATE Worker behind a service binding rather than co-locating it with the edge paywall, and watch startup_time_ms in every wrangler deploy output. Second, you will ship two copies of zod — @x402/core pins ^3.24.2 while @modelcontextprotocol/server pins ^4.2.0. Splitting the MCP server into its own Worker solves this too; if you keep them together, alias zod@3 onto zod 4.6.5's ./v3 subpath and test the x402 parse paths carefully. Both of these argue for the same structural decision, which is why I would make it now rather than after the first 10021.


## mcp-on-workers — WORKS_WITH_CAVEATS

Hosting Musebook's remote MCP server on Cloudflare Workers works, and works better than on Vercel — but plan section 7's package choice should change. I unpacked mcp-handler 2.2.0 from npm: it is a ~450-line shim (12.9 KB ESM) over `createMcpHandler` from `@modelcontextprotocol/server` 2.0.0, with ZERO `node:` imports, ZERO `next/*` imports, and `next` marked optional in `peerDependenciesMeta`, so it does run on workerd. But it adds nothing you want on Workers and omits the one thing you must have: the MCP spec requires the server to validate browser `Origin`/`Host`, and the official SDK entry is explicitly "validation-free" — mcp-handler never adds it, so a bare Worker mount would be DNS-rebinding-vulnerable. Cloudflare's `agents` 0.24.0 ships `createMcpHandler` from `agents/mcp/server`, which wraps the exact same SDK entry and adds route matching, CORS, Host/Origin validation, `workers-oauth-provider` props plumbing, and a `notify` API. Both therefore implement MCP revision 2026-07-28 identically (the revision logic lives in `@modelcontextprotocol/server`, which ships both the 2026-07-28 modern codec and the legacy 2025 codec, plus a dedicated `workerd` export condition). `McpAgent` is DEPRECATED and feature-frozen as of agents 0.20.0 — its Durable Object session state is legacy, exactly as you suspected. Recommendation: drop mcp-handler, use `agents/mcp/server` + `@modelcontextprotocol/server@2.0.0`, no Durable Objects, on a separate `musebook-mcp` Worker at mcp.musebook.dev.

**Recommendation:** Rewrite plan section 7 as follows.

STACK: `agents@0.24.0` (import from `agents/mcp/server`) + `@modelcontextprotocol/server@2.0.0` (exact) + `zod@4.6.5` + `postgres@3.4.9`, on a dedicated `musebook-mcp` Worker at mcp.musebook.dev, compatibility_date 2026-09-21, no compatibility_flags, NO Durable Objects, NO Next.js route. Drop `mcp-handler` from the dependency list.

WHY NOT mcp-handler, honestly: it does run on workerd — I read the tarball and it is clean, 12.9 KB, no node builtins, no next imports, next peer optional. It is not broken and it is not a trap. It just becomes redundant, because both it and Cloudflare's wrapper call the exact same `createMcpHandler` from `@modelcontextprotocol/server@2.0.0`. The protocol question you flagged as CRITICAL turns out to be a non-differentiator: 2026-07-28 support lives in the SDK, and both wrappers inherit it identically, including the required `_meta` envelope, required `resultType`, `server/discover`, and MRTR replacing server-initiated requests. What separates them is Workers-shaped: Cloudflare's wrapper adds the Origin/Host validation that the SDK deliberately omits and the MCP spec requires, plus `route`, CORS, `env`/`ctx` threading, and the workers-oauth-provider props handoff. mcp-handler adds proxy-header origin detection and analytics hooks that are Vercel-shaped. On Cloudflare, Cloudflare's wrapper wins on merit, not on branding.

WHY NOT McpAgent: your suspicion is correct and the answer is stronger than "still needed?" — McpAgent is formally deprecated and feature-frozen as of agents 0.20.0 (2026-07-27), pinned to the old `@modelcontextprotocol/sdk@1.30.0` with Zod-only schemas. Its per-session Durable Object existed to hold `Mcp-Session-Id` state that 2026-07-28 abolished. Do not provision `durable_objects` or a `new_sqlite_classes` migration for MCP. That removes a whole class of cost and cold-start from the plan.

OAUTH: use `@cloudflare/workers-oauth-provider@0.10.3` wrapping the MCP handler (`apiRoute: "/mcp"`), not `withMcpAuth`. It is a full OAuth 2.1 authorization server — RFC 9728 protected-resource metadata, RFC 8414 AS metadata, RFC 7591 dynamic client registration (which MCP clients genuinely need, since they register themselves), PKCE, and grant storage in the `OAUTH_KV` namespace. `withMcpAuth` is only a bearer verifier and would leave you to build issuance, consent, and DCR by hand. Write your tool authorization against `getMcpAuthContext()?.props`, not `context.http.authInfo`, until workers-oauth-provider ships the verified-context symbol agents is already looking for.

SEQUENCING: set `legacy: "stateless"` now so 2025-era clients keep working through the migration, and flip to `legacy: "reject"` once telemetry shows no envelope-less traffic. Keep the Hyperdrive binding in this Worker so tools read Supabase directly rather than round-tripping through the Vercel origin — that is the main latency win from moving MCP off Vercel, and it composes with the rest of the split architecture. Two things to write down as constraints, not surprises: MCP change-notifications are isolate-local (no cross-isolate fan-out, `bus` is blocked by the wrapper), and there is no server→client request channel in 2026-07-28, so any confirm-before-charge x402 flow must be modeled as MRTR `inputRequired`, not elicitation.

**Blockers:**
- None that stop the design. The split architecture's MCP leg is the easiest part of the move.
- Soft blocker on plan section 7 as written: it names `mcp-handler 2.2.0 + @modelcontextprotocol/server 2.0.0 + zod 4.2, mounted at a Next.js route`. If MCP moves to Cloudflare, mcp-handler stops earning its place — it contributes only `onEvent` analytics hooks, proxy-header origin detection (`x-forwarded-host`, which is a Vercel-behind-proxy concern, not a Worker concern), an experimental WebMCP browser bridge, and `withMcpAuth`. On a Worker you lose nothing by dropping it and you gain the Origin/Host validation the MCP spec requires.
- Real caveat to design around: `context.http.authInfo` is NOT populated by workers-oauth-provider 0.10.3 (it sets `ctx.props` but not the verified-context Symbol agents looks for). Authorize Musebook tools off `getMcpAuthContext()?.props`, and do not write code that depends on `authInfo.clientId`/`authInfo.scopes` until a workers-oauth-provider release ships the symbol.
- Real caveat: `subscriptions/listen` change notifications are isolate-local and the Agents wrapper forbids the SDK's `bus` option. If a tool mutation in one isolate must push `tools/list_changed` to a subscriber pinned to another isolate, this stack cannot do it. Design Musebook's MCP tools to be poll-shaped, not push-shaped.
- Real caveat: the 2026-07-28 revision has no server→client request channel. Anything in the plan that assumed server-initiated `elicitation` or `sampling` (e.g. asking the agent to confirm an x402 charge mid-tool-call) must be restructured as MRTR / `inputRequired` multi-round-trip, or served on a separate legacy sessionful route. The SDK throws loudly rather than silently degrading, so this will surface at the first call, not in production.
- Not a blocker but decide it now: put the MCP server on its own Worker (mcp.musebook.dev), not inside the edge Worker that fronts Vercel. The edge Worker is the hot path for every page GET; the MCP Worker carries the MCP SDK, OAuth provider, and a Postgres driver. Separate Workers = separate bundles, separate cpu_ms, separate blast radius, and the OAuth KV binding stays off the hot path.


## observability-cost — WORKS_WITH_CAVEATS

The Cloudflare side of the split architecture is dramatically cheaper than the plan's Vercel-everywhere model: roughly $5/mo at launch, $11/mo at 10k DAU, and ~$114/mo at 100k DAU — against the plan's current $1,895/mo Vercel subtotal at 100k DAU. The dominant saving is R2's free egress: at the stated media assumptions (28.8 TB/mo at 100k DAU) Vercel Fast Data Transfer at $0.15/GB would bill ~$4,170/mo for the same bytes, and R2 bills $0. Analytics Engine should take the telemetry firehose: at $0.25/million data points (billing not yet enabled as of the pricing page's last revision, so effectively $0 today) 204M events/mo costs $48.50, versus ~108 GB/mo of new Postgres heap+index and a sustained ~95 inserts/sec that forces a compute-tier jump on Supabase. But AE cannot replace `action_events` wholesale — it retains only 3 months and applies its own sampling, so spine invariant 3's slate/label data must stay in Postgres. For logging, Workers Logs (20M events/mo included, 7-day max retention) is the hot-debug store only; the 30-day archive §15.15 asks for is Logpush→R2 at $0.05/million requests, which kills the plan's speculative $200/mo aggregator line. The alerting story is the weak spot: Cloudflare's only relevant native notification is a dollar-threshold Budget Alert, there is no hard spend cap, and every one of the four silent failure modes §15.19 identifies must be built as a Cron Trigger Worker querying Analytics Engine plus `env.QUEUE.metrics()`, cross-watched against the existing pg_cron evaluator.

**Recommendation:** Rewrite §15.15-15.22 around four decisions. (1) STRUCTURED LOGGING: keep the 60-line first-party JSON logger and its redaction exactly as written — it is correct and portable — but change the destination. Workers Logs with observability.enabled=true becomes the 7-day hot store at head_sampling_rate 0.1 on the human pass-through path and 1.0 on a separate un-sampled money/agent Worker; Logpush (workers_trace_events) to an R2 bucket becomes the 30-day archive at $2.30/mo; Sentry stays for diagnosis via the native OTLP destination with persist:false so traces are not double-billed. Delete the '$200/mo log aggregator, vendor unchosen' line and the Vercel Log Drain entirely. Do NOT use Tail Workers for log shipping — native OTLP export supersedes them; keep Tail Workers only if you later need custom pre-export filtering. (2) TELEMETRY: split the firehose. Analytics Engine takes impressions, dwell heartbeats, scroll, agent crawl events and route-class telemetry — about 85% of the 79.5 events per DAU per day — written with writeDataPoint, never awaited, with sample_rate carried in double3 per §13.4.1. Postgres keeps the slates and slate_items rows (which ARE the served-order record invariant 3 actually protects), every engagement and negative-feedback action, every play_through, and every money event. A nightly worker reads Analytics Engine over the SQL API and writes action_events_daily and the dwell histograms — the rollup tables §13.7.2 already defines. This is a firm recommendation: it saves $200-$500/month at 100k DAU, cuts the database's sustained write rate from ~95/sec to ~16/sec, shrinks monthly disk growth from 108 GB to ~18 GB, and removes the impression stream from the same failure domain as the payment ledger. Keep TELEMETRY_IMPRESSION_SAMPLE as the knob but note it now moves the Analytics Engine bill, not gigabytes of disk. (3) COST MODEL: replace §15.21/15.22 wholesale. The Cloudflare side is $5 / $11 / $114 per month at the three scales with every line item priced above; Vercel drops from $1,895 to ~$287 at 100k DAU once three of the four apps and all media move off it; the grand total goes from $5,413 to ~$1,600. Add the explicit media assumptions (0.5 MB stored per post, 200 KB served per media object, 6 media objects per page view, 90% edge cache hit) so the numbers are falsifiable, and correct the Supabase line to $25/month per organization with a $10 compute credit. Add three named traps as design rules: never route telemetry through Queues ($295/mo at scale), never leave log sampling at 1.0 ($89/mo at scale), and never route /_next/static/* through the Worker (it multiplies billed requests roughly sevenfold). (4) ALERTING: keep pg_cron + pg_net as the PRIMARY evaluator — the reasoning in §15.19 that it survives a total serving-plane outage is still right, and it is now more right because it also survives a Cloudflare outage. Add a secondary Cron Trigger Worker on a 5-minute cadence that queries Analytics Engine for paywall-fail-open and ranking-rung distribution, and calls env.QUEUE.metrics() for backlogCount and oldest-message age. Cross-watch the two: each evaluator has one rule that fires when the other's heartbeat goes stale. Add a Cloudflare Budget Alert at 2x and 4x the modeled spend as the only cost guardrail that exists, and pair it with a ja4-keyed WAF rate limit and a KV kill-switch, because Cloudflare has no pause-on-limit. Settlement-failure detection needs no change — those events are in Postgres and pg_cron already sees them.

**Blockers:**
- Analytics Engine CANNOT be the canonical training log. It retains only 3 months and applies its own sampling (exposed as _sample_interval), so it cannot satisfy spine invariant 3 — 'every action_events row has non-null slate_id, position, weights_version, model_version, from the first slate ever served, and the counterfactual is unrecoverable if omitted'. The slates/slate_items rows and every label-bearing event must stay in Postgres, or be Logpush-archived to R2 as Parquet before the 3-month window closes. Any design that puts the whole firehose in AE and nothing in Postgres loses the training window permanently.
- There is NO hard spend cap on Cloudflare. Budget alerts are advisory, evaluated daily on projected spend, and fire once per billing cycle — there is no equivalent to Vercel's pause-on-limit. A crawl flood against free posts is unbounded Workers-request cost. §15.24's 'Vercel spend limit' control does not port; it must be replaced by a WAF rate-limit rule keyed on ja4 plus a KV kill-switch the edge Worker reads on every request, and §15.19's A23 must be re-pointed at a Cloudflare Budget Alert plus a GraphQL-derived request-rate rule.
- Workers Logs maxes out at 7 days of retention. §15.15 specifies 30 days. Workers Logs alone cannot meet that requirement at any price — the 30-day store must be Logpush to R2 (or an OTLP destination with persist:false), and §15.15's 'UNVERIFIED aggregator' fallback should be rewritten to name Logpush-to-R2 as the primary rather than a Vercel Blob drain.
- No native Cloudflare notification covers any of the four silent failure modes §15.19 identifies. Paywall-fails-open, settlement failure, queue backlog and ranking fallback are all custom detection work. This is not a blocker to the architecture but it is unbudgeted engineering: roughly one Cron Trigger Worker, one AE dataset with a stable schema, and one new pg_cron rule for the cross-watch.
- Cloudflare pay-per-crawl's plan requirement (Free vs Pro vs Business vs Enterprise zone) could not be verified — the docs domain is egress-blocked and the MCP search returned nothing on it. This matters because the DNS move assumes a Free zone is sufficient. SAFE FALLBACK: the plan already implements the 402 challenge and settlement itself in the edge Worker, so pay-per-crawl is an optimization, not a dependency; ship on the Free zone with the Worker's own paywall and evaluate pay-per-crawl separately.
- Analytics Engine billing is not yet enabled and Cloudflare has given no enablement date. The $48.50/mo scale line is a forecast at published rates, not a current charge. Budget for it; do not plan around it being free, and set a Budget Alert that would catch the month it switches on.
